# P22 operational board integration proposal

15/10/2026 · WBS-029 · UC-35/37/38 · EXT-NOSITTER. This proposal extends the [P01 v1 API](p01-api-permission-contract-v1.md); it does not silently modify the shared schema, DTO registry, Visit/Offer models or global route registrations. P01/P34 must approve the read/remedy mapping before production composition. P21 remains owner of dispatch/Offer rules; P20 read projections are not yet merged at the starting base.

## Exported interfaces

`createVisitBoardService({ repository, scopePort, clock })` exports list, detail, proposeRemedy, respondRemedy and manualAssign. `createVisitBoardRouter({ service, sessionPort, allowedOrigins })` exports an Express router mounted beneath `/api/v1` by P34 only after the real ports are ready. `StaffVisitBoardPage` uses `createVisitBoardApi` and the shared cookie/CSRF/no-store client. It has no fixture fallback and does not register itself in AppRoutes. P48 owns the header/sidebar shell.

| Route proposal | Actor / input / result |
| --- | --- |
| GET /staff/visit-board | Staff/Admin operational scope; fromAt/toAt required zoned instants, window≤31days, kind/state/areaCode/needsAction, limit1–50 default20, opaque cursor≤512; items + nextCursor + timeZone |
| GET /visits/{id}/dispatch | Staff/Admin scoped detail; one latest remedy including content, createdAt, response and respondedAt; no unbounded history |
| POST /visits/{id}/remedies | Staff/Admin; expectedVersion, message1–1000, alternatives1–5 unique future slots; Idempotency-Key; 201 pending proposal, visitResolved=false |
| POST /visits/{id}/remedies/{remedyId}/responses | Customer owner only; expectedVersion, remedyVersion, choice CONFIRM_SLOT/DECLINE, alternativeId, confirmed=true for slot choice, response message; server timestamp |
| POST /visits/{id}/assignments | Existing P01 canonical command; Staff/Admin; expectedVersion, sitterId, reason, Idempotency-Key; P34 must choose one handler, not mount competing P21/P22 handlers |

HTTP visit IDs are canonical lowercase ObjectId strings. Domain ports accept bounded identifiers compatible with P21; remedy IDs generated by the service are UUIDs (proposal, not a changed P01 canonical entity). All writes use the P06 session/role/Origin/CSRF middleware; unknown body fields including owner/actor/area grant are rejected. Every operation key is server-scoped to actor and fingerprinted normalized payload, including Visit version. Replay returns the committed result only after rechecking actor/scope and Visit ownership. No raw storage/provider errors are returned.

Kinds PROPOSAL/BOOKING/OFFER/VISIT/CASE have separate P01 state sets. `needsAction` and `remedyState` are separate fields; no combined orderStatus. List items allow only id/kind/state/areaCode/startAt/visitId/bookingId/version/serviceName/petCount/needsAction/remedyState. Contact, exact address, access notes, pet medical data, evidence and private Staff notes are excluded even if the repository accidentally returns them. Details are scoped and return the most recent remedy, not a Customer's unrelated history. Staff access is an operational need, never blanket customer-data access. Admin inherits Staff but still receives area grants from scopePort, not request fields.

## Required repository contract (not implemented by fixtures)

`scopePort.resolve(actor)` returns authoritative `{areaCodes, version}` with at most100areas. It must use current server grants, not an array supplied by HTTP or a long-lived client token. Empty grants deny access. Production list/detail must revalidate session/authEpoch/grants for each request; mutations must revalidate again inside the transaction.

`repository.list({ actor, actorId, scope, filter, cursor, limit, fetchLimit, projection })` receives the authenticated server session for revalidation and applies all filters, scope and projections on the server, with deterministic `(startAt, kind, id)` seek ordering. Scope/filter-bound signed or server-stored cursors reject tampering and reuse across actors or changed grants/filters. No offset scan or unbounded find→filter in JavaScript. fetchLimit≤51; return≤limit rows and null/opaque nextCursor, not an unlimited count/history. Candidate indexes/query plans are a P34/P44 task against the final P19/P20 schema; P22 does not invent explain/load results. The service independently rejects oversized/out-of-scope/wrong-filter rows before serialization and rechecks session expiry after the read. HTTP responses are private/no-store and vary on Cookie, including error responses.

`repository.detail({ actor, visitId, scope, remedyLimit:1 })` returns a current scoped Visit plus at most one associated remedy. Projection must include Visit version and server-derived area/customer/service data; wrong ownership/area produces404. It must not read all booking pets/cases to build a detail response.

`repository.runGuarded({ actor, visitId, scope, sitterId }, callback)` must run a real Mongo transaction with bounded retry of write conflicts, not an in-memory mutex. Before callback reads eligibility, write the same sitter-level EligibilityGuard and sorted sitter-day occupancy guards used by P21/P24/P18/suspension. Acquire Visit CAS and scope/session guards. For remedy confirmation, acquire old/new-day guards before schedule changes. On commit, recheck policy/payment/directed confirmation, active offers, intervals [start,end), configured travel buffer, reservations and current Visit version. All corresponding writers must touch the same guards; snapshot reads alone are insufficient for racing acceptance or suspension.

The callback requires these transaction-bound methods:

- authorize({actor,scope}): reload current session/authEpoch/roles/operational grant or Customer ownership; throw on revocation.
- getVisit, getCandidate, getPendingRemedy, getRemedy: current scoped snapshots. getCandidate must include approval, active User/Sitter status, services/area, availability/dayOff and buffered overlap conflict; missing hard gates fail closed through P21.
- findOperation / recordOperation: actor-key unique operation record, normalized fingerprint and replay result; persisted in the same transaction. Do not expire/deduplicate an operation while it can be retried against an uncertain outcome without a documented outbox retention policy.
- validateAlternativeSlots: recheck P19/P18 policy and availability, plus P25/P51 decisions when changing a paid schedule. Missing decisions must throw an explicit decision gate; no invented reschedule cutoff, slot hold or fee/refund. Proposal creation does not reserve or change the original schedule and does not create an Offer.
- createRemedy: unique pending remedy per Visit, durable pending content/alternatives/reason/timestamp/customer/visitVersion/version; reject duplicates under race. updateRemedy: CAS remedy version and pending state, store Customer response timestamp.
- confirmAlternativeSlot: atomically create/update the Customer-confirmed schedule proposal under P19/P42/P25 ownership, invalidate stale offers and apply schedule/allocation only if that contract allows it. Customer confirmation cannot manufacture an accepted assignment. An unavailable decision/payment/availability means rollback and a safe error.
- assignVisit: CAS current SCHEDULED/no-sitter Visit to ASSIGNED, version+1, expire/revoke competing pending Offers atomically. Validate the same candidate again under held guards. One assignment per Visit and occupied slot. No fake COMPLETED/earning/payment write.
- appendAuditAndOutbox: transaction-bound immutable actor/event/resource/time plus appropriately scoped notification, dedup by committed operation; record remedy content/response via remedy reference. Queue delivery after commit through P33, never call email/SMS while holding transaction guards. An audit/outbox failure rolls back the domain change and operation record.

Service manual assignment additionally requires future SCHEDULED/unassigned Visit, no pending Customer remedy, known originalVisitCount, verified payment for multi-visit booking, and a known directed flag. Directed assignment requires Customer-confirmed proposal matching current Visit version, exact slot and selected sitter. A changed availability/suspension or an occupied slot must lose the same transaction guard race. Ranking results outside that transaction cannot authorize assignment.

## Pending and unknown outcomes

Remedy stays PENDING_CUSTOMER_CONFIRMATION while Customer has not responded. CONFIRM_SLOT requires an explicit confirmation and one proposed future slot, plus fresh validation. DECLINE records feedback but leaves the Visit unresolved. CUSTOMER_CONFIRMED still means visitResolved=false and does not mean sitter accepted or booking complete. No automatic Offer is created before Customer confirmation in a directed flow. P21 may dispatch only after confirmation/payment/availability gates and after the transaction commits.

UTC instants are stored/transmitted; filtering and display use Vietnam UTC+7 (`Asia/Ho_Chi_Minh`, equivalent local service zone to Asia/Saigon). UI uses an exclusive next-local-midnight interval and ignores host timezone; no naive browser Date parsing of datetime-local. On202/timeout/network error or malformed write acknowledgment, show pending and block resend/optimistic assignment. The current page requires reconciling the result before a new mutation; P34 must expose operation/outbox status for robust recovery across reloads. Durable CAS/unique pending remedy/idempotency remain authoritative across processes.

## Integration gate

P20 must publish its read projection implementation; P34/P01 must provide the concrete Visit/Offer/remedy/operation/guard/audit/outbox repositories, schema/index migrations, contract approval and routing. P22 tests verify service/HTTP orchestration and UI with synthetic ports, not Mongo race safety, notification delivery or full Customer flow. No live provider config or new package dependency is required by this independent module. Production enablement remains INTEGRATION_PENDING until the above gate is verified.

This is a production enablement gate. The independently exported service/router/page can be reviewed and merged without enabling it: it imports no P20 module, does not register production routes and has no fixture fallback. P21/P04 code is already merged. P34 must keep the runtime disabled until the concrete contracts and integrated checks above are complete; merging this proposal does not approve those shared schemas or any open business decision.
