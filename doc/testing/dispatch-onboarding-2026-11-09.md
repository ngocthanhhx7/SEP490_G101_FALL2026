# Dispatch and new employee readiness

## Findings and design

A read-only production census on 2026-11-09 found 4 Pet Sitter accounts, 2 registered employee calendars and 0 matching capability profiles. The reported capability rejection occurs before ranking. Application service wishes are not verified competence; no capability or completed job is backfilled.

Staff/Admin can verify services, species, care traits, pet count and weight limits from the employee management capability tab, after an active approved employee and current signed contract are checked. A reason, expected version and actor-scoped idempotency key are mandatory. The command reuses `aisitterprofiles`, employee guards, `employeeschedulecommands` and `employeescheduleevents`. It preserves registered calendar, leave and daily origins. The service catalog is bounded to 60, trait catalog to 100; no collection, index or native validator changes are introduced. Existing unique userId and transactional guards remain authoritative. No automatic migration or production data write is required by deployment.

The dispatch detail shows current-time manual candidates immediately, one selected employee per invitation, individual first blocking reasons and a profile link. This preview uses existing manual-invitation eligibility: contract, service/pet capability, registered area/hours, leave, occupancy, daily/weekly hours and adjacent travel. It does not require the daily outward/return origin used by automatic dispatch. MANUAL preview cannot change booked time or area. Customer-directed bookings only expose the customer's employee. Invitation creation and acceptance recheck current conditions. The preview is advisory; it reserves no slot and assigns no employee.

Alternative-time previews and automatic invitations continue to require the daily origin and route evidence. Only the owning customer's confirmation changes a booked time. Sitters now declare their own day origin using a chosen map pin and same-day availability, within 31 days. Entries are bounded to 31 current/future dates; old origins are pruned only when that employee saves a declaration. Coordinates stay private and are omitted from schedule audit events.

## Cold start algorithm

Eligibility and ranking are separate. Operational dispatch has no minimum rating, previous-job count or learned-score threshold. Existing model advice may reorder only the complete eligible set; missing advice/timeouts retain the deterministic route/workload fallback. Manual candidates prioritize lower weekly work minutes then stable identity, independent of ratings. A newly verified employee can receive and accept a first invitation with zero outcome/review rows. The invitation group targets five employees, falling back to fewer only when the eligible pool is smaller. No allocation quota or rating is invented, and no job is promised before employee acceptance.

Google documents candidate generation, scoring and re-ranking as separate stages, with freshness/fairness considered in re-ranking: [recommendation architecture](https://developers.google.com/machine-learning/recommendation/overview/types). It also describes the cold-start limitation of collaborative filtering for unseen items: [collaborative filtering limitations](https://developers.google.com/machine-learning/recommendation/collaborative/summary). These sources inform the separation; they do not prescribe Paw World Care's eligibility, employment or financial policies.

## Storage and rollout

The live capability userId query uses the existing unique index (empty collection: 0 keys/documents examined, 0 ms); the existing area availability lookup remains bounded at 101 records and fails explicitly beyond 100. At this population no new index is justified. All Staff previews retain the existing six-per-minute rate limit and private/no-store responses.

Validate session/role/CSRF, idempotent replay/conflicting key, stale version, directed selection, no forced assignment, self-only origins and authoritative acceptance on isolated synthetic fixtures. Run architecture, both lints, full tests and frontend build before review. Use independently reviewed main, exact artifact, fresh backup and isolated restore, then normal blue/green activation. Before the owner repair, rollback can use the previous code. After superseding a future contract, rollback must retain superseded-contract-aware backend readers; prefer a reviewed forward fix and never revive an old backend blindly or restore a stale database over new writes. Live employees still require real Staff verification and their own availability declarations; deployment does not fabricate those decisions.

UI follows a single-choice radio group with an explicit legend and no automatic first selection: [GOV.UK radios](https://design-system.service.gov.uk/components/radios/). Each blocked candidate explains the first failed authoritative check and opens the relevant management tab.
